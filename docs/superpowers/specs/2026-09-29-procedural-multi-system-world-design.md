# 随机多黑洞恒星世界设计

日期：2026-09-29

状态：设计已确认，等待实施计划

适用项目：`D:\Codex\orbital`

## 1. 目标

把当前固定的“单黑洞 + 九颗恒星”世界升级为可重新生成的随机多系统世界。每个世界包含 2–4 个固定黑洞，每个黑洞拥有 3–7 颗按规定轨道公转的恒星，恒星总数不超过 24。所有黑洞和恒星都真实参与卫星引力与碰撞；天体之间不做 N 体相互作用。

世界只在用户主动执行“重新生成星系”时改变。普通服务重启必须恢复同一套世界。每次重新生成都会永久删除旧世界的全部卫星、轨迹、事件和导出，避免旧历史与新引力场错配。

## 2. 已确认的产品规则

- 采用“静态黑洞中心 + 规定恒星轨道”的分层模型。
- 黑洞固定在世界坐标中；恒星只绕各自宿主黑洞运动。
- 卫星受到全部黑洞和全部恒星的引力。
- 黑洞和恒星均可捕获卫星，并记录具体撞击天体。
- 黑洞数量随机为 2–4 个。
- 每个黑洞的恒星数量随机为 3–7 颗，全世界最多 24 颗恒星。
- 黑洞的质量、视觉尺寸和吸积盘风格不同；恒星的质量、体积、颜色、轨道距离和相位不同。
- 重新生成由显式按钮触发，不随服务启动自动发生。
- 重置必须二次确认，并删除旧世界全部卫星相关数据。

## 3. 不采用的方案

### 3.1 仅由最近星系产生引力

该方案计算量较低，但卫星跨越系统边界时引力会不连续，轨迹会出现不自然跳变，因此不采用。

### 3.2 完整 N 体天体运动

让黑洞和恒星彼此影响会显著增加计算、碰撞、存档与回放复杂度，并产生混沌且难以复现的世界演化。当前产品目标是丰富、确定、可回放的多系统场景，因此不采用。

### 3.3 每次服务启动重新随机

该方案会让已有卫星历史与当前星图不一致，并把普通重启变成隐式数据删除，因此不采用。

## 4. 世界配置与版本

服务端保存一个活动世界配置，至少包含：

- `worldId`：不可复用的世界标识。
- `version`：生成格式版本，例如 `procedural-multi-system-v1`。
- `seed`：生成此世界的确定性随机种子。
- `generation`：递增的世界代数。
- `createdAt`：创建时间。
- `blackHoles`：黑洞定义数组。
- `stars`：恒星定义数组，每颗恒星含 `hostBlackHoleId`。
- `observation`：世界统一可观测边界。

黑洞定义至少包含 `id、name、x、y、solarMass、mu、schwarzschildRadius、captureRadius、diskHue、diskTilt、diskScale`。恒星定义至少包含 `id、name、hostBlackHoleId、orbitRadius、massRatio、mu、collisionRadius、phase、angularSpeed、periodTicks、color`。

同一个生成器版本与同一个种子必须产生字节级等价的黑洞和恒星定义。随机数生成器必须由项目代码固定实现，不能依赖运行时可能变化的 `Math.random()` 行为。

卫星持久化记录附带 `worldId` 和世界生成版本。正常情况下数据库只保留活动世界的卫星；该字段用于一致性校验、备份诊断和拒绝意外混入的旧数据。

## 5. 随机生成约束

世界原点保留一个主黑洞，以维持坐标基准、初始视角和现有操作习惯。主黑洞质量随机为 10–20 个标称太阳质量；另外 1–3 个次级黑洞随机为 5–15 个标称太阳质量。`mu`、史瓦西半径和捕获半径按质量比例计算，不能继续共享单一黑洞参数。

次级黑洞位于可观测区域内的不同方向和距离。生成器为每个系统先分配系统包络，再放置恒星轨道：

- 任意两个黑洞的系统包络不得重叠，并保留额外视觉与发射通道间距。
- 恒星最小轨道半径不得小于宿主黑洞稳定轨道下限和捕获半径安全倍数。
- 恒星最大轨道半径不得超过宿主系统包络，也不得进入相邻黑洞的保留区。
- 同一宿主的相邻恒星轨道必须保持最小比例间距，避免视觉拥挤。
- 恒星碰撞半径必须小于相邻轨道间距，并与其质量和视觉类型一致。
- 所有黑洞与恒星定义必须为有限值、标识唯一、名称唯一，并位于可观察范围内。

生成器最多尝试固定次数。无法满足约束时必须返回失败，不能输出部分合法的世界。候选世界失败不会影响当前世界。

## 6. 物理模型

每个黑洞使用自己的 Paczyński–Wiita 势。对卫星位置 `p`，第 `i` 个黑洞的加速度使用该黑洞自己的 `mu_i` 和 `r_s_i` 计算；恒星继续使用带软化长度的牛顿点吸引子。卫星总加速度为所有黑洞与所有恒星贡献之和。

每颗恒星只根据宿主黑洞质量、轨道半径、初始相位和世界时钟计算规定圆轨道。计算恒星轨道时忽略其他黑洞和恒星的扰动，这是已确认的模型近似，必须在模型元数据与导出说明中披露。

每个积分 tick 只生成一次全体动态恒星状态，并在该 tick 的所有卫星之间共享。起点和终点天体状态分别缓存，Velocity Verlet 积分不得为每颗卫星重复构造恒星对象。

碰撞检测对积分线段与所有黑洞捕获边界、恒星表面执行最早交点搜索。若同一积分步存在多个候选碰撞，选择子步时间最早者，并记录 `bodyType、bodyId、bodyName、bodyX、bodyY、fieldTick、substepFraction`。

黑洞和恒星不因卫星质量发生位移，卫星之间也不相互作用。统一可观测边界仍决定卫星何时离开场景；它不是引力截断边界。

## 7. 运行时边界

生成器与物理模块分离：

- `world-generator` 只根据版本和种子生成、验证不可变世界配置。
- `simulation` 根据传入的世界配置计算天体状态、引力、碰撞和卫星积分，不读取数据库或 DOM。
- `engine` 负责加载活动世界、推进世界时钟、持久化卫星并执行原子重置。
- 浏览器通过模型接口获取活动世界配置，不再把固定九星列表当作唯一真相。

服务端和浏览器必须使用相同的共享世界配置与轨道函数。浏览器不得独立重新随机，也不得通过种子猜测服务端世界；种子用于确定性验证，持久化配置才是运行时真相。

模型接口和实时快照返回 `worldId`。浏览器发现 `worldId` 改变时，立即清除卫星、历史、选择、轨迹 GPU 缓冲和旧天体视觉缓存，再加载新世界。

## 8. 视觉与相机

每个黑洞使用同一个可复用渲染器与预生成吸积盘纹理，通过单独的质量、史瓦西半径、色相、倾角和视觉比例绘制。视觉放大只影响渲染，不改变碰撞半径和引力参数。

恒星继续使用粒子日冕效果，但远距离恒星允许按屏幕尺寸降低粒子和弧线细节。该降级只改变视觉复杂度，不减少物理天体，也不改变恒星核心尺寸层级。

地图为每个黑洞显示可点击定位标记。原点主黑洞仍可作为坐标参考，但文案不能再把它称为唯一黑洞。“重置视野”根据全部系统包络计算相机范围，使所有黑洞系统可见。

发射坐标、拖拽、缩放、跟踪卫星和历史轨迹继续使用统一世界坐标。轨道参考环改为围绕各自黑洞绘制，并在低缩放级别减少不必要的环线。

## 9. 重置界面与权限

在卫星档案区域增加危险样式的“重新生成星系”按钮。第一次点击打开说明，明确列出将永久删除：

- 所有运行中和已结束卫星；
- 所有轨迹热数据与压缩归档；
- 所有生命周期事件；
- 所有待处理和已完成导出；
- 当前随机世界配置。

用户必须输入确认短语并再次提交。重置期间禁用发射、终止、删除、导出和重复重置操作，并显示阶段状态。

重置接口使用 `POST /api/world/reset`，必须通过现有会话与 CSRF 校验。当前产品是本机服务，接口还必须验证请求来自回环地址；若未来允许远程部署，必须先引入独立管理员授权，不能把全局重置权限授予普通访客身份。

## 10. 原子重置与文件清理

重置顺序如下：

1. 在内存中生成并完整验证候选世界。
2. 获取全局重置锁，拒绝新的发射、终止、删除和导出任务。
3. 停止推进并提交当前数据库事务，取消或结束导出 worker。
4. 在一个数据库事务中删除卫星、热轨迹、事件、归档清单和导出记录，写入候选世界并递增代数。
5. 数据库提交成功后原子切换内存世界，清空采样器与卫星缓存并恢复推进。
6. 广播新的 `worldId`，使所有页面清空旧状态并重新加载模型。
7. 删除已经失去数据库引用的轨迹压缩包和导出文件。

候选生成、验证或数据库事务失败时，旧世界和旧数据必须完整保留。数据库提交后的文件删除失败不会回滚新世界；失败文件登记为孤立文件，并由启动清理和后续重试删除。数据库记录永远不能引用已删除文件。

## 11. 升级与兼容

升级现有数据库时不自动删除用户数据。若数据库没有活动世界记录，程序把当前固定单黑洞九恒星布局登记为 `legacy-fixed-nine-v1` 世界，并让现有卫星引用该世界。普通重启继续得到与升级前相同的引力场。

用户首次主动重置后才生成 `procedural-multi-system-v1` 世界并清除旧卫星数据。新世界使用新的模型与动力学版本；旧版布局兼容代码至少保留到明确的数据迁移版本，不得静默用随机世界解释旧轨迹。

服务启动仍执行严格版本检查。缺失、损坏或约束不合法的世界配置必须阻止推进并给出可恢复错误，不能静默重新随机。

## 12. 性能策略与门槛

最大世界包含 4 个黑洞和 24 颗恒星，共 28 个引力源。相对于当前 1 个黑洞和 9 颗恒星，单颗卫星的引力循环约增加到 2–3 倍。

首轮实现采用以下优化边界：

- 每个 tick 的天体状态只计算一次并跨卫星共享。
- 热路径使用紧凑、稳定的数据布局，避免为每个吸引子创建临时对象。
- 碰撞先使用包围距离做廉价排除，再求精确线段交点。
- 浏览器复用黑洞纹理与渐变资源；远处恒星降低粒子细节。
- 历史轨迹继续使用独立 WebGL 图层，不恢复逐帧 Canvas 复制。

服务端验收门槛：最大 28 个引力源和 1000 颗活跃卫星时，推进 1 模拟秒的中位耗时低于 0.8 秒，在基准机器上至少保留 20% 实时余量。基准必须预热并报告多轮结果，不能用单次冷启动数据通过门槛。

浏览器验收门槛：在当前开发机器的全景视角显示最大世界和典型卫星数量时，交互与回放帧率不低于 45 FPS。若不达标，先减少远处恒星的粒子与轨道环细节；不得降低物理步频、减少已生成天体或跳过远处天体引力。

## 13. API 与实时同步

`GET /api/model` 返回静态物理常量、活动世界配置、世界版本和服务器时钟。发射请求必须携带客户端当前 `worldId`；不匹配时返回冲突并要求刷新，防止重置瞬间把卫星发射到错误世界。

`POST /api/world/reset` 接收确认短语和客户端当前 `worldId`。世界不匹配、已有重置进行中、非回环请求、CSRF 失败或确认短语错误时拒绝请求。

实时快照和事件包含 `worldId`。重置成功后发送世界重置通知；旧世界的迟到请求、导出完成消息和流事件必须通过 `worldId` 或会话代数检查丢弃。

轨迹与导出接口只访问当前世界卫星。因为重置会删除旧卫星，所以旧 URL 返回不存在，而不是把旧记录映射到新世界。

## 14. 错误处理

- 随机约束在固定尝试次数内无法满足：保持旧世界并返回可读错误。
- 世界配置包含重复 ID、非有限值、越界天体或非法轨道：拒绝加载并阻止推进。
- 重置数据库事务失败：回滚全部数据库变化并恢复旧世界推进。
- 文件清理失败：保留新世界，记录孤立文件并安排重试。
- 浏览器收到未知世界版本：停止发射与回放，提示刷新或升级，不使用部分兼容模式。
- 页面在重置期间断线：重连后通过 `worldId` 变化执行完整本地清理。
- 性能基准未达到门槛：不得以降低物理正确性通过；先优化共享缓存和数据布局，仍失败时回到设计评审。

## 15. 测试与验收

自动测试至少覆盖：

- 相同生成器版本和种子产生完全相同的世界。
- 黑洞为 2–4 个，每系统恒星为 3–7 颗，总数不超过 24。
- 黑洞包络、恒星轨道、相邻间距、碰撞半径和可观测范围全部满足约束。
- 多黑洞 Paczyński–Wiita 加速度与多恒星软化引力正确叠加。
- 规定恒星轨道只依赖宿主、世界时钟与持久化配置。
- 同一步多个碰撞候选选择最早交点，并记录正确天体。
- 普通重启保持同一 `worldId`、种子和天体状态。
- 现有数据库升级为旧世界配置时不改写历史轨迹。
- 重置成功后旧卫星、轨迹、事件、归档和导出均不可访问。
- 候选生成失败和事务失败时旧世界、旧数据保持完整。
- 文件删除失败形成可重试孤立文件，不留下数据库悬空引用。
- 浏览器检测世界变化后清空列表、历史、选中状态和 GPU 轨迹。
- 历史回放在同一世界 tick 得到与实时一致的恒星位置和碰撞位置。
- 旧世界的迟到网络响应不能污染新世界界面。
- 最大世界的服务端基准满足 0.8 秒门槛。

浏览器人工验证至少覆盖：

- 2、3、4 个黑洞世界均能完整显示和定位。
- 重置确认、忙碌状态、成功通知与失败恢复清晰。
- 全景、近景、拖拽、缩放、跟踪和历史回放均可用。
- 最大世界在当前开发机器上保持至少 45 FPS。
- 远处视觉降级不会改变恒星尺寸层级或让天体消失。

完成后运行现有全部自动测试，确认历史轨迹、导出、备份、恢复、删除记录、固定步长积分和 Windows 启动器不受影响。

## 16. 不在本次范围内

- 黑洞或恒星之间的 N 体相互作用。
- 黑洞合并、恒星演化、超新星或潮汐破坏。
- 多世界并存、切换旧世界或恢复已删除世界。
- 为普通远程用户提供全局世界重置权限。
- 动态降低物理步频或忽略远处引力源。
- 在重置后保留或迁移旧卫星历史。
