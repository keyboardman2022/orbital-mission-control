# 单颗卫星轨迹存储预算设计

日期：2026-09-20  
状态：已确认设计，等待实现计划  
适用项目：`D:\Codex\orbital`

## 1. 目标

为每颗卫星设置约 100 MiB 的终身轨迹存储预算。轨迹达到预算后，卫星继续在服务器中计算，当前位置、速度、存活时间和生命周期状态继续更新，但不再保存新的轨迹坐标。历史回放与导出只覆盖从出生到预算耗尽时最后一个已保存点的过程。

本功能控制轨迹历史的增长，不改变物理积分、可观测区域、卫星状态持久化、用户身份或卫星之间互不影响的规则。

## 2. 预算定义

SQLite 的数据页、索引页和碎片空间由多颗卫星共享，无法可靠归属到单颗卫星。因此本功能使用确定性的轨迹点预算：

- 名义预算：`104,857,600` 字节，即 100 MiB。
- 保守折算：每个已保存轨迹点计 `256` 字节。
- 每颗卫星最多保存 `409,600` 个轨迹点。
- 出生点、普通采样点和轨迹终态点都计入点数。
- 已转移到 gzip 归档的轨迹点仍占用终身额度；压缩与归档不会重置预算。

界面使用“约 100 MiB”描述该限制，不宣称它等于SQLite文件中可精确测量的物理空间。

## 3. 持久化模型

预算信息保存在现有卫星 `record` JSON 中，不新增数据库表：

```json
{
  "trajectoryBudget": {
    "version": "point-budget-v1",
    "limitBytes": 104857600,
    "estimatedBytesPerPoint": 256,
    "maxPoints": 409600,
    "status": "recording",
    "cappedAt": null
  }
}
```

达到上限时更新为：

```json
{
  "status": "capped",
  "cappedAt": {
    "seq": 409600,
    "tick": 123456,
    "elapsedSeconds": 514.4
  }
}
```

`seq` 继续作为已保存点数及顺序的权威来源。轨迹封顶后不再递增。卫星的运行状态仍使用 `active`、`captured`、`out_of_observable` 或 `terminated`，轨迹是否封顶是独立维度。

## 4. 写入流程

新卫星出生时附带预算策略。每次采样器准备写入保留点时，服务器执行以下步骤：

1. 如果卫星已经封顶，丢弃轨迹候选点，不向 `points` 或轨迹归档追加数据。
2. 如果尚未封顶，按现有事务写入下一个点并递增 `seq`。
3. 当 `seq` 达到 `409,600`，把这个点作为最后一个轨迹点，记录 `cappedAt`，关闭该卫星的轨迹采样器。
4. 同一次采样器刷新中剩余的候选点全部丢弃。

封顶后固定步长积分仍以 240 Hz 推进。现有卫星 `record` 行继续被覆盖更新，以支持重启恢复和实时遥测；这不会产生随运行时间增长的新轨迹行。

捕获、越界和人工终止仍可保存小型生命周期事件以及卫星最终状态，但不得向轨迹点集合追加坐标。这样可以知道卫星最终发生了什么，同时保证历史轨迹严格停在封顶点。

## 5. 重启与旧数据兼容

启动时按以下规则恢复：

- 带有 `trajectoryBudget` 的卫星直接恢复其策略和状态。
- 旧卫星没有预算字段时，根据现有 `seq` 补充 `point-budget-v1` 策略。
- 若旧卫星 `seq >= 409600`，立即标记为封顶，不创建采样器。
- 若 `seq < 409600`，从剩余额度继续记录。
- 归档清单不需要逐文件扫描，因为归档点在归档前已经获得连续的 `seq`，卫星记录中的序号不会因归档删除热数据而回退。

策略只向前应用，不改写或删除已经保存的历史点。

## 6. API与界面

卫星公共记录增加轨迹覆盖信息：

```json
{
  "trajectoryCoverage": {
    "status": "recording",
    "estimatedBytes": 1024000,
    "limitBytes": 104857600,
    "maxPoints": 409600,
    "lastSeq": 4000,
    "endTick": 40000,
    "endElapsedSeconds": 166.67
  }
}
```

封顶后 `status` 为 `capped`，覆盖终点固定为 `cappedAt`。卫星详情显示“轨迹记录已达约 100 MiB 上限”，并同时显示卫星仍在运行时的当前遥测。

历史时间轴的最大值使用 `trajectoryCoverage.endElapsedSeconds`，不能使用晚于轨迹末端的卫星当前存活时间。用户不会拖入没有轨迹数据的区间。

## 7. 查询与导出

轨迹查询继续合并SQLite热数据和gzip归档。查询范围必须截断到覆盖终点，返回值携带 `trajectoryCoverage`，使客户端能够区分“轨迹结束”与“卫星生命周期结束”。

导出规则：

- 未封顶卫星：维持当前行为，导出截至请求时刻的轨迹。
- 已封顶卫星：只导出出生点至 `cappedAt.seq` 的轨迹点。
- JSON顶层元数据及CSV首行的元数据字段写入覆盖范围、名义预算、封顶原因和封顶时间。
- 导出中的卫星档案可以包含较晚的当前或最终状态，但必须明确指出该状态晚于轨迹覆盖终点，不能把轨迹描述为完整生命周期记录。
- 导出任务不得为了建立截止点而给已封顶卫星追加采样点。

## 8. 错误处理和一致性

- 最后一个轨迹点与 `trajectoryBudget.status = capped` 必须在同一数据库事务中提交，避免重启后多写或少标记。
- 如果事务失败，内存中的封顶状态不能先于数据库提交成为唯一事实；下一次检查应安全重试。
- 封顶是幂等操作。重复检查不会改变 `cappedAt`，也不会增加 `seq`。
- 备份继续包含卫星记录、SQLite热数据和gzip归档，无需新增备份文件类型。
- 环境配置若允许修改预算，只影响新卫星；每颗卫星在出生时固定策略，防止运行期间改变上限造成歧义。第一版默认值固定为100 MiB，不增加页面配置项。

## 9. 验证

自动测试至少覆盖：

- 第409,600个点被保存并成为覆盖终点，后续点不再写入。
- 同一次采样器刷新跨越上限时不会超额。
- 封顶后推进、检查点和服务器重启不会增加轨迹点，当前状态仍继续前进。
- 卫星随后捕获、越界或人工终止时，轨迹末端不变，生命周期状态正常保存。
- gzip归档不会释放或重置额度。
- 旧卫星在上限以下继续记录，在上限以上立即封顶。
- 历史时间轴停在覆盖终点，页面显示轨迹截断与当前遥测的区别。
- JSON与CSV只包含覆盖范围内的点，并带有明确的截断元数据。
- 并发检查点、备份和导出保持固定截止序号，不出现重复点或越界读取。
